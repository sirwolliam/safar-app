## 1. Product summary

Safar is a companion app for Muslims preparing for and undertaking Hajj or Umrah. Audience skews toward first-time pilgrims, often older and less tech-comfortable, frequently anxious in the lead-up. Design priorities that follow: **calm, legible, low cognitive load, high contrast, simple navigation.**

The app is organized around **Four Pillars**: Learn, Practice, Plan, Connect — surfaced as cards on the Home screen, each opening a Hub. ("Practice" is the chosen spelling app-wide, Americanized from British "Practise.")

## 2. Tech & conventions

- **Framework:** React Native via Expo.
- **Navigation:** `@react-navigation` — bottom tabs + native stacks.
- **Storage:** `@react-native-async-storage/async-storage`.
- **Icons:** `phosphor-react-native`. ALWAYS verify an icon name exists before use (e.g. `Kaaba` and `Dove` do NOT exist; use `Mosque`, `HandHeart`, `StarAndCrescent`). No emoji in UI.
- **SVG:** `react-native-svg`.
- **Font:** `SourceSerif4-Regular` (constant `SERIF`).
- **Other deps in use:** `expo-haptics`, `react-native-safe-area-context`, `expo-linear-gradient`, `expo-notifications` (guarded — wrapped in `try/require`, falls back to a "dev build required" alert if unavailable), `expo-image-picker` (guarded, same pattern).
- **Shared standalone modules (new convention, this session):** small cross-screen logic/data — e.g. `prayerSettings.js`, `TripDetailsEditor.jsx` — live at the project root next to `theme.js`/`AccessibilityContext.js`, not inside `screens/`. `screens/*.jsx` import them with `../`.
- **Firebase (`firebase.js`):** `auth` and `db` are currently both stubbed to `null` — **there is no live backend yet.** All "account" data (name, email, avatar, journey type, departure date) is local `AsyncStorage` only. User has stated Firebase setup is planned soon — real Settings/Account work (sign-out, change password, delete account) is blocked until then.

### Coding rules (hard-won)
1. `StyleSheet.create` at module level.
2. **No `&&` in style arrays** — use ternaries. `style={cond ? [a, b] : a}`, never `style={[a, cond && b]}`. Same caution for `&&` rendering JSX children when the left side could be `0` or `""`.
3. Phosphor icons only, verified to exist. No emoji.
4. After edits: `npx expo start --clear` (Metro caches aggressively; `--clear` is required to see changes).
5. Verify JSX parses before delivering.
6. Propose design in plain language and get sign-off before coding (esp. anything structural/visual).
7. Read the existing file — and grep for the SPECIFIC feature — before writing, to avoid duplicating an existing section.
8. **Don't reproduce fabricated Islamic content.** Arabic, translations, hadith citations must come from real sources; unverified entries flagged `verified:false` pending qualified human review. **This session caught two live violations of this rule** — see §8.5 (Lesson content corrections) — Claude Code had generated unsourced ritual detail (Idtiba'/Ramal specifics, an invented "pour water over your head" Zamzam instruction, an overstated Arafah-sunset fiqh ruling) that wasn't in the source material. Always diff delivered content against the actual source, not just against what the prompt asked for.
9. **Don't build two independent mechanisms that can hold conflicting state for the same fact.** This session hit this repeatedly: a fake "Journey Reminders" toggle unconnected to the real notification permission flow in `PrayerTimesScreen`; journey type editable via inline pills in one sheet while a shared editor also existed; three separate un-cross-referenced "step lists" for the same pilgrimage. When adding a control for something that already has a source of truth elsewhere, wire to the *same* storage key / same component, don't duplicate.

## 7. Design principles (agreed)

- **Pillars = cards, not pills.** Use pills only for filterable content (Du'ā library, Media).
- **Hub link cards:** uniform MEDIUM rich cards (~90–110px, photo + title + one-line desc) — "premium but not huge."
- **Card cohesion principle:** shared "grammar" (radius/shadow/border/spacing/type tokens) + deliberate 1–2 variable deviations for hierarchy.
- **Match the app's existing card style** rather than inventing new looks.
- Low cognitive load, high contrast, large legible text — the audience skews older.
- Don't over-design; live with changes on device before iterating further.
- **Real-time vs. preparation-time usage (added this session).** Almost nothing in this app is actually used mid-ritual. Pilgrims are engaged with their surroundings and devotion, not their phones, once a rite is underway. The exceptions are du'ās (read in-hand throughout) and the physical counters — Dhikr, Tawaf, Sa'i — which are genuinely used live, mid-count. Everything else — Lesson Flow, the Pilgrimage Map, Sacred Places, guides — is a before/after tool: studied in preparation, referenced in idle moments (in the tent, in line, the night before), or reviewed afterward. Design accordingly: these screens can afford real depth and a calmer pace rather than being optimized for split-second glanceability, while du'ās and counters should stay optimized for fast, one-handed, mid-ritual use.

## 8. Lesson Flow System

*Folded in from SAFAR_HANDOFF_LESSON_FLOW.md, updated with this session's completion and one reversed decision.*

**Status: complete both guides.** Umrah 10/10, Hajj 16/16 — matching, fully built and verified lesson-by-lesson.

### 8.1 What it is
A reusable, data-driven multi-screen lesson pager used by both guides. One shared component (`LessonFlowScreen.jsx`) renders any lesson from an ordered array of typed "blocks" in that lesson's own content file. Adding a lesson means writing a content file — it does **not** mean touching the component, unless a genuinely new block type is needed.

### 8.2 Files
- `screens/LessonFlowScreen.jsx` — the pager: block renderers, header, footer, swipe/navigation.
- `screens/LessonListScreen.jsx` — lesson index, data-driven via `guide` route param, reads `LESSONS` map + `GUIDE_META`.
- `lessonProgressStore.js` — AsyncStorage progress tracking, `{furthestIndex, total}` per lessonId, written on every screen change.
- `content/lessons/lesson_umrah_01.js`–`_10.js`, `lesson_hajj_01.js`–`_16.js` — one file per lesson.
- `content/lessons/index.js` — imports every lesson file, exports flat `LESSONS` map (`"umrah-01"`, `"hajj-16"`, etc.). **Must be updated every time a lesson file is added.**

### 8.3 Navigation wiring
- `App.js` registers `"LessonList"` and `"LessonFlow"` inside the Learn stack.
- Both guide screens' hero cards → `navigate("LessonList", { guide })`.
- `LessonListScreen` → tapping a lesson → `"LessonFlow", { lessonId }`.
- **Every back button in `LessonFlowScreen` — cover, interior header, and now `moment` — navigates explicitly to `"LessonList", { guide: lesson.guide }`.** This is a correction from the original handoff: `moment`'s back button originally stepped back one screen (`onStepBack`) rather than exiting to the list, reasoned as "not an entry/exit point." Mid-session the user was explicit this should behave like every other back button — always exit to the list, no exceptions — so this was reversed. The bottom `‹ X of Y ›` chevrons remain the only way to step screen-by-screen.
- The "Return to Lesson Menu" button was also corrected this session: it previously called `navigation?.goBack?.()` (worked by coincidence, since `"Next Lesson"` uses `.replace()` rather than `.navigate()` so stack depth never grew) — now calls the same explicit `navigate("LessonList", {guide})` as every other exit, removing a latent fragility.
- "Next Lesson" (last screen only) uses `navigation.replace("LessonFlow", { lessonId: nextLessonId })`, computed from `guide + "-" + padded(lessonNumber + 1)`. If the next lesson doesn't exist, the button doesn't render — only "Return to Lesson Menu" shows. This is correct behavior on Hajj Lesson 16 now (true end of guide), same as it correctly was on Lesson 6 before 7–16 existed.

### 8.4 Block type schema (11 types)
Every block renders inside the shared header/footer **except** `cover`, `closing`, `moment` (full-bleed, chrome-suppressed — see §8.4a).

| Type | Purpose | Key fields |
|---|---|---|
| `cover` | First screen | `image` (optional), `lessonBadge`, `title`, `subtitle`, `readingMinutes` |
| `cardList` | Icon + label rows | `title`, `cards: [{id, icon, label}]` |
| `qaCardList` | Q&A cards | `title`, `cards: [{id, question, answer}]` |
| `narrativeText` | Icon/image + paragraphs | `title`, `icon`, `paragraphs: [string \| {heading}]` |
| `bulletList` | Two-column numbered tile grid | `title`, `bullets: [string]` (only Umrah Lesson 1 uses this) |
| `numberedSteps` | Numbered step cards | `title`, `steps: [{heading, body}]` or richer `{heading, tagline, body, bullets}` |
| `duaList` | Icon + du'a topic bullets + optional CTA | `title`, `duas: [string]`, optional CTA fields |
| `companionTool` | Sage-green CTA card | `title`, `description`, `ctaLabel`, `ctaScreen`, `ctaTab`/`ctaMode` |
| `insight` | Cream/gold pull-quote | `title`, `text`. **Reused convention (this session):** the same block type is used up to 4× per lesson with different titles — "A Moment to Notice," "Insight," "Reflection," and "My Notes Prompt" (the last with `icon: "NotePencil"`) — rather than inventing new block types for visually-identical content. |
| `closing` | Full-bleed final screen | `image`, `quote`, `references: [string]`. Used on Umrah Lesson 10 and now also Hajj Lesson 16 (true end of both guides). |
| `moment` | Full-bleed mid-lesson beat | `image`, `quote`. Back button now exits to list (see §8.3) — no longer step-back. |

#### 8.4a Full-bleed image screens
`cover`, `closing`, `moment` share one visual family: `ImageBackground` + `CoverScrim` (SVG gradient) + white text, gated by:
```js
const hasFullBleedImage = activeBlock.type === "cover" || activeBlock.type === "closing" || activeBlock.type === "moment";
```
Controls arch/pattern header visibility, footer transparency, and text color. Any future full-bleed type must be added to this condition.

### 8.5 Content policy learned this session
Claude Code, when asked to expand/rewrite lesson content, twice introduced unsourced specifics not present in the actual source PDFs (fabricated Idtiba'/Ramal detail with an invented hadith attribution; a "pour Zamzam water over your head" instruction not in the cited Ibn Majah hadith — verified directly against sunnah.com; an overstated Arafah-sunset fiqh ruling). **All lesson content must be traceable to the actual uploaded source material** — when Claude drafts prompts for new lessons, transcribe/lightly copyedit the source, don't let Claude Code "enrich" it. When a person flags a specific ruling as needing correction, verify against a primary source before editing (this session used sunnah.com directly for the Zamzam hadith).

### 8.6 Known open items
1. **Cover→interior swipe transition glitch** — still deliberately deferred (arch header snaps in rather than animating). Revisit now that all 26 lessons exist and there's real title-length variety to tune against.
2. **`SacredPlacesScreen` still doesn't include Mina, Arafah, or Muzdalifah as browsable sites.** Partially addressed sideways this session — see §10 — new locator-map images for these three locations exist and are being used inside the (in-progress) Pilgrimage Map redesign instead of as Sacred Places entries. Whether they should *also* become Sacred Places entries is still an open product question.
3. **Five Hajj lessons ship with no Companion Tool CTA**, by deliberate decision, not oversight: Lessons 9 (Mina) and 12 (Jamarat/Mina) — no matching Sacred Places location; Lessons 13 (Sacrifice & Renewal), 14 (Tawaf al-Ifadah), 15 (Farewell Tawaf) — informational/rulings content with no matching destination screen anywhere in the app. This is a real content gap worth a dedicated conversation about whether the app needs a general Hajj-rulings reference screen.
4. `GuideCarousel.jsx` is confirmed dead code (see §4) — cleanup (deletion) still not executed, low priority.
5. Progress tracking writes on cover view too (`furthestIndex: 0` on open, before advancing) — deliberate, distinguishes "started" from "never opened."
6. No per-lesson unique closing/moment images — Umrah 10's `closing` and Hajj 6's `moment` and Hajj 16's `closing` all reuse that lesson's own cover image. Easy swap later if distinct art is supplied.

## 9. Settings & Shared Editors

*New this session.*

### 9.1 Profile editing (`SettingsScreen.jsx`)
Ported from the orphaned `ProfileScreen.jsx` (was the root screen of a "Prepare" tab that may be retired — the working avatar-grid + edit-sheet code was still intact there and reused rather than rebuilt). Now lives as a "Profile" row at the top of Settings — avatar thumbnail + name, tap opens a bottom sheet (name, email, avatar picker with 16 built-in options + custom photo via guarded `expo-image-picker`). **Journey type is no longer edited here** — moved to Trip Details (§9.3) to avoid two mechanisms editing the same field (see Coding Rule 9).

### 9.2 Prayer Times settings
`PrayerTimesScreen.jsx` calls the Aladhan API (free, no key). Previously: calculation `method` was hardcoded local state (`useState(4)`, never persisted), no Asr madhab (`school`) parameter existed at all, and the notify button requested permission but never actually scheduled anything.

Now: `prayerSettings.js` (shared module) exports `PRAYER_METHODS` (5 curated methods, default Umm al-Qura), `PRAYER_SCHOOLS` (Standard / Hanafi), and the three AsyncStorage keys (`safar_prayer_method_v1`, `safar_prayer_school_v1`, `safar_prayer_notify_v1`). Both `PrayerTimesScreen` and `SettingsScreen` read/write the same keys, so they can't disagree. Settings exposes: a Calculation Method picker (modal, radio-row + checkmark pattern), an Asr Calculation selector (stacked full-width rows with checkmark — **not** side-by-side pills, which visibly truncated the longer "Standard (Shafi'i, Maliki, Hanbali)" label), and a "Prayer Time Reminders" toggle.

**Known limit, stated explicitly so it isn't mistaken for done:** the toggle correctly requests permission and persists preference — but **no actual notification-scheduling logic exists yet.** Prayer times shift daily and depend on location, so real scheduling needs its own refresh strategy (compute next N days, reschedule) — deliberately scoped out of this pass to avoid quietly shipping another toggle that "looks functional but isn't."

**Removed:** the old "Journey Reminders" toggle in Settings — was `useState(true)` with zero persistence and zero connection to any real notification system. Confirmed via grep this was the *only* other notification-related UI in the app besides Prayer Times' own (also-broken, now-fixed) button.

### 9.3 Trip Details — shared editor (`TripDetailsEditor.jsx`)
New shared component (project root, not `screens/`) — journey type pills (Umrah/Hajj/Learning) + a Year→Month→Day picker lifted from `OnboardingFlow.jsx`'s `DepartureDateScreen` (re-skinned to match Settings' palette). Writes directly to `safar_journey_type_v1` / `safar_departure_date_v1`. Mounted from two places, both calling the exact same component:
- **Home:** pencil icon on the "My Journey" card (§5).
- **Settings:** a "Trip Details" row, its own section, separate from the Profile card.

Before this, journey type was only editable via Settings' Profile sheet (no departure date editing anywhere post-onboarding), and departure date wasn't editable anywhere after initial onboarding at all — `OnboardingFlow.jsx` is a one-time linear wizard, not reopenable. "Restart Setup" technically allowed changing it but forced the entire 6-screen flow to fix one date.

**Bug fixed this session:** initial hydration of a malformed/partial stored date (year+month but no valid day) rendered "NaN" in the summary — added `Number.isFinite` guards on parse in `TripDetailsEditor`, `HomeScreen`'s countdown calc, and `SettingsScreen`'s Trip Details row display, so a bad stored value now falls back gracefully instead of displaying garbage. If "NaN" reappears anywhere, it likely means a still-corrupted value is sitting in storage from before this fix — re-saving the date clears it.

### 9.4 Accessibility toggles — audited, not yet fixed
`AccessibilityContext.js`: **High Contrast is real** (swaps an actual color palette). **Large Text and Reduce Motion are not** — both toggle state that nothing downstream reads. Reduce Motion does correctly auto-initialize from the OS-level setting via `AccessibilityInfo.isReduceMotionEnabled()`, which is a nice touch, but still isn't acted on anywhere. **User wants both wired up properly — deferred until after Firebase setup**, per explicit instruction this session.

### 9.5 Other Settings audit findings — deferred, not fixed
- **Data & Privacy controls** (export data / delete all data) — none exist. No analytics/tracking library exists anywhere in the codebase (verified by grep — the one "analytics" hit was `DhikrScreen.jsx`'s own local count stats, not third-party), so any privacy copy written can honestly say nothing leaves the device. Deferred until after Firebase setup.
- **Language, Privacy Policy, Terms of Service rows** all navigate to `screen={null}` — dead-end taps. No i18n infrastructure exists anywhere. Recommendation (not yet actioned): remove the decorative "Language" row until real; Privacy Policy/Terms need real content from the user/counsel before they can be wired to anything.
- **"Clear Trip Data (Test)"** — a dev-only debug button, self-labeled "temporary testing button" in its own Alert copy, sitting in production Settings. Flagged, not yet removed/gated.
- Dead `Trash` icon import removed from `SettingsScreen.jsx` during the profile-port pass.

## 10. Sacred Places — Locator Maps

*New this session.*

`SacredPlacesScreen.jsx`'s `SiteCard` had an existing but entirely unpopulated `locatorMap`/`markerPos` scaffold (image + pin-overlay). Swipe navigation between sites (already existed via `PanResponder` on the hero image, alongside arrows and chip-tap) was confirmed working, not rebuilt.

## 11. Pilgrimage Map (`MapScreen.jsx`) — Redesign In Progress, Not Yet Built

*New this session. Design decisions only — implementation has not started.*

### 11.1 Problems found in the current implementation
- **All 12 steps (6 Umrah + 6 Hajj) share one identical map image** (`Umrah_map_test1.png`, filename itself a placeholder tell). For Hajj steps — Mina, Arafat, Muzdalifah, kilometers apart in reality — the pulsing dot sits at made-up coordinates on an image that doesn't depict those places at all. Actively misleading, ranked as the top priority fix, above any visual polish.
- Step descriptions are hard-capped at `numberOfLines={2}` with no way to read the rest — real instructional content silently truncated.
- The intended photo→map fade gradient doesn't render — `photoFade` style sets `backgroundColor: "transparent"`, a no-op; `expo-linear-gradient` is already a working dependency elsewhere and should be used for a real fix.
- **Layout stacks three visual registers at once** (real photo, full-bleed illustrated map, floating card) with heavy overlay chrome — assessed as the likely core reason the page "doesn't feel right," separate from the map-accuracy problem.

### 11.2 A third, orphaned step-list system was discovered mid-redesign
`GuideCarousel.jsx` — a full-screen cinematic swipeable guide (12 Hajj / 8 Umrah steps, photo + animated title + description + source citation) — was still referenced by both guide screens' hero cards as recently as the start of this session, advertising step counts ("12 steps," "7 steps") that matched neither Lesson Flow (16/10) nor Map (6/6). **Confirmed this session: both guide screens now open Lesson Flow instead, and `GuideCarousel` is fully unimported/orphaned** — same situation as `ProfileScreen.jsx`. Two live bugs from this stale wiring were found and fixed (§4). Net result: the product is down to two non-competing systems — Lesson Flow (depth) and Map (physical orientation) — which is what the redesign below assumes.

### 11.3 Agreed redesign direction (not yet built)
- **Map's one job:** "where am I, physically, right now" — not a second copy of Lesson Flow's depth.
- **List-first entry screen** (doesn't exist yet): steps in correct sequential order, each with a thumbnail photo, tap into detail.
- **Detail card stays slim, no forced scrolling:** photo + accurate map + a short 2–3 line description. Full instructions and du'ās become one-tap links *out* to the matching Lesson and the du'a player, rather than duplicated inline — avoiding a third independently-maintained copy of the same instructions (Coding Rule 9).
- **Navigation within steps:** keep arrows + pips + swipe — this exact combination is already proven in three places in this app (Sacred Places `SiteCard`, Lesson Flow pager, Map's own current stepper); reuse the pattern, don't reinvent it.
- **Umrah/Hajj toggle removed.** Map will be reached separately from each guide screen (already the case via the half-cards), so the mode is already known from context — no manual switcher needed. (If Map ever gets a standalone entry point outside the two guide screens, it should default to the person's own `journeyType` from Trip Details rather than reintroducing a toggle.)
- **Map imagery:** reuse the already-made `SP_mina`, `SP_arafah`, `SP_muzadalifah` Sacred Places locator images directly for the matching Hajj steps (same real places, correct scale, already on-brand) rather than regenerating. For Umrah's steps (all within Masjid al-Haram), one accurate diagram at the "Kaaba & X" scale, matching the quality bar the person already set with the Sacred Places images, can likely serve all six with different marked positions — pending the person generating that art, same workflow as the Sacred Places batch.

- Whether Umrah's 6 steps share one map image or need more than one, pending seeing the new art.
